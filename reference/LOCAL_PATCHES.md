# Local patches to openpi

Local modifications to the upstream openpi checkout (base commit `15a9616`) made to fine-tune
π0 with LoRA on a LeRobot **v3.0**-format dataset
(`harrison-powe/hello-hands-cube-pick-place_20260804_190811`) on Python 3.11 + CUDA.

Every change is marked in-file with a `LOCAL PATCH:` comment so it can be found with
`grep -rn "LOCAL PATCH" .`

---

## Root cause

Upstream pins lerobot to git rev `0cf864870cf29f4738d3ade893e6fd13fbd7cdb5` (version `0.1.0`),
whose `CODEBASE_VERSION` is `v2.1`. Loading a `v3.0` dataset raises `ForwardCompatibilityError`.

The obvious upgrade (`lerobot==0.6.0`) is closed: lerobot `>=0.5.0` requires Python `>=3.12`,
and this venv is Python 3.11.10.

**Resolution:** lerobot `0.4.x` is the newest line that supports **both** `CODEBASE_VERSION = "v3.0"`
and `Requires-Python: >=3.10`. Verified by reading the wheel metadata / source directly:

| lerobot | Requires-Python | CODEBASE_VERSION |
| ------- | --------------- | ---------------- |
| 0.1.0   | >=3.10,<4.0     | v2.1             |
| 0.3.3   | >=3.10          | v2.1             |
| 0.4.0   | >=3.10          | **v3.0**         |
| 0.4.4   | >=3.10          | **v3.0**         |
| 0.5.0+  | **>=3.12**      | v3.0             |

No dataset conversion and no Python 3.12 venv rebuild were needed.

## 1. `pyproject.toml`

### 1a. lerobot source: git rev -> PyPI 0.4.4

```diff
-    "lerobot",
+    "lerobot>=0.4.4,<0.5.0",
```

```diff
 [tool.uv.sources]
-lerobot = { git = "https://github.com/huggingface/lerobot", rev = "0cf864870cf29f4738d3ade893e6fd13fbd7cdb5" }
```

### 1b. `requires-python` narrowed to `>=3.11,<3.12`

```diff
-requires-python = ">=3.11"
+requires-python = ">=3.11,<3.12"
```

With the open-ended range, `uv lock` also resolves a `python_full_version >= '3.13'` split.
`numpy<2.0.0` (which openpi pins) has no cp313 wheels, so that split was unsatisfiable once
lerobot 0.4.x entered the graph. The repo already ships `.python-version == 3.11`, so this
narrowing matches the environment that is actually built.

### 1c. `rerun-sdk` override

```diff
 [tool.uv]
-override-dependencies = ["ml-dtypes==0.4.1", "tensorstore==0.1.74"]
+override-dependencies = ["ml-dtypes==0.4.1", "tensorstore==0.1.74", "rerun-sdk==0.23.1"]
```

lerobot 0.4.4 requires `rerun-sdk>=0.24.0,<0.27.0`, and **every** release in that range declares
`Requires-Dist: numpy >=2`, which conflicts with openpi's `numpy>=1.22.4,<2.0.0`.
`rerun-sdk==0.23.1` is the newest release still declaring `numpy>=1.23` (no upper-bound-2 pin).
rerun is only used by lerobot's dataset-visualization scripts, never by the training data path.

### 1d. `uv.lock`

Regenerated by `uv lock`. On linux/x86_64 the CUDA stack is byte-for-byte unchanged
(`jax==0.5.3`, `jax-cuda12-pjrt==0.5.3`, `jax-cuda12-plugin==0.5.3`, `nvidia-cublas-cu12==12.6.4.1`,
`nvidia-cudnn-cu12==9.5.1.17`, `nvidia-nccl-cu12==2.26.2`, ...). The nvidia entries that `uv lock`
reported as "removed" were the `platform_machine == 'aarch64'` / `sys_platform == 'darwin'`
marker variants only, dropped along with the non-3.11 resolution splits.

Notable package moves: `lerobot 0.1.0 -> 0.4.4`, `datasets 3.6.0 -> 4.8.5`,
`huggingface-hub 0.32.3 -> 0.35.3`, `pyarrow 20.0.0 -> 25.0.0`, `wandb 0.19.11 -> 0.24.2`,
`gymnasium 0.29.1 -> 1.3.0`. `torch==2.7.1`, `torchvision==0.22.1`, `torchcodec==0.4.0`,
`transformers==4.53.2` and `numpy==1.26.4` are unchanged.

## 2. `src/openpi/training/data_loader.py`

### 2a. Import path (line ~10)

```diff
-import lerobot.common.datasets.lerobot_dataset as lerobot_dataset
+import lerobot.datasets.lerobot_dataset as lerobot_dataset
```

lerobot moved this module out of the `common` subpackage in 0.3.0.

### 2b. New `_task_index_to_prompt()` helper, used in `create_torch_dataset()`

```diff
-        dataset = TransformedDataset(dataset, [_transforms.PromptFromLeRobotTask(dataset_meta.tasks)])
+        dataset = TransformedDataset(
+            dataset, [_transforms.PromptFromLeRobotTask(_task_index_to_prompt(dataset_meta.tasks))]
+        )
```

`transforms.PromptFromLeRobotTask` documents and requires `tasks: dict[int, str]` and calls
`self.tasks.get(task_index)`.

* lerobot 0.1.0 stored tasks in `meta/tasks.jsonl` and exposed `dict[int, str]`.
* Since the v3.0 format they live in `meta/tasks.parquet` and are exposed as a **pandas
  DataFrame indexed by the task string** with a single `task_index` column — i.e. the *inverse*
  mapping. `.get(0)` therefore returned `None` and training died with
  `ValueError: task_index=0 not found in task mapping`.

The helper inverts the DataFrame back to `{int: str}` and passes a plain `dict` through
unchanged, so `transforms.py` keeps its documented contract and needs no edit.

## 3. System package (outside the repo and the venv)

```sh
apt-get install -y ffmpeg   # 7:4.4.2-0ubuntu0.22.04.1 on Ubuntu 22.04
```

lerobot 0.4.4 decodes video with `torchcodec`, which dlopens the FFmpeg shared libraries at
import time (`libavutil.so.56` for FFmpeg 4). None were present, so every `__getitem__` raised
`RuntimeError: Could not load libtorchcodec`.

This mirrors what openpi's own CI does — see
[`.github/workflows/test.yml:19`](.github/workflows/test.yml#L19):
`sudo apt-get install -y ffmpeg libavcodec-dev libavformat-dev libavutil-dev`.

The dataset's videos are **AV1** (`video.codec: av1`); Ubuntu's FFmpeg 4.4 build includes
`libdav1d`, so decoding works — verified by decoding real frames out of
`videos/observation.images.scene/chunk-000/file-000.mp4`.

## 4. Runtime environment (no source change, but required)

The container disk (`/` overlay) is only **20 GB**. The `pi0_base` checkpoint is **12.01 GB across
24 files**, which does not fit alongside the 7.7 GB venv, so the first training attempt died with
`OSError: [Errno 28] No space left on device` mid-download.

Fix — export before training so openpi caches assets on the network volume:

```sh
export OPENPI_DATA_HOME=/workspace/openpi_cache
```

`get_cache_dir()` in [`src/openpi/shared/download.py:26`](src/openpi/shared/download.py#L26) reads
this env var (default `~/.cache/openpi`). 24 large files download to the network volume without
hitting the "stale file handle" problem that afflicts many-small-file installs there.

`checkpoint_base_dir` already defaults to `./checkpoints` (i.e. `/workspace/openpi/checkpoints`),
so training checkpoints land on the network volume without any change.

Space was also reclaimed with `uv cache clean` (~9 GB) after the sync completed.
